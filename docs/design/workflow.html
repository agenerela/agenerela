Building an Agenerela agent, start to finish

What a game developer actually does with our framework: every file they create, every GameObject they add, every window they open, and the exact line where their code takes over from ours. Nine steps, from an empty Unity project to a guard that answers a player.

The nine steps

two of them happen once per project

Four bands. A developer moves left to right once, then loops between the last two forever. Every step is tagged with what it produces: a project asset, a C# file, something in the scene, or a window they look at.

Band A · Set up, once per project

≈ 5 minutes

Nothing here is about a particular agent. It is done once, by one person, and everybody else on the game inherits it.

Step 01 — Install the package

One dependency line. Our own demo games use a relative file: path because they live in this repo; an outside developer would use a Git URL or a tarball.

Packages/manifest.json
"dependencies": {
  "com.agenerela.framework": "file:../../../UnityProject/Packages/com.agenerela.framework",
  "com.unity.nuget.newtonsoft-json": "3.2.1",  // pulled in by us, not by you
  ...
}

Then add Agenerela to the game's own asmdef, so game code can see the API. No scoped registry, no OpenUPM, no native binaries — the in-process provider that needs those is a separate opt-in package later.

Step 02 — Point at a model

Somewhere the developer types localhost:11434 and picks a model. Today no screen in our six-screen map owns that — the Agent Behaviour inspector shows a provider dropdown, but a dropdown per agent means the URL, timeout and budget cap get retyped on every guard in the scene.

Proposal: a provider config asset, plus a Project Settings page that names the project default. An asset, not a settings singleton, because Phase 4 needs to run two configurations against each other in one session — arm A and arm B have to be nameable, droppable objects.

Band B · Author the agent

two front doors, one result

Describing what an agent is and what it can do. Nothing here mentions the scene, a handler or a model. It can be done entirely in one script, or entirely in assets a designer edits without opening C# — and the framework cannot tell the difference afterwards.

Step 03 — Define each verb

Two ways to do this, and both are supported (DR-011). In code, each action is a tagged method on one script — no assets at all, and the minimum agent becomes one file. Or as an asset: right-click in the Project window → Create ▸ Agenerela ▸ Action Definition. Both produce the same ActionDefinition in the same registry, and nothing downstream can tell which was used. Where both define the same id, the asset wins — so you can start in code and drop in an asset later for just the action whose wording you want to measure.

◆
Why keep the asset path at all: description and example wording is what Phase 4 A/B-tests. Text inside a C# attribute cannot be swapped between arm A and arm B without a recompile, so the harness could not drive it — and no writer on the team could edit it.

Whichever door you use, the fields are the same. The Id becomes the literal string the model is allowed to emit. The description is the only thing the model reads about this action, which is why its length is checked: an emphatic paragraph on one option measurably drags a small model toward that option.

Step 04 — One Agent Profile per kind of agent

This is screen 1 from the sketch lab. Identity fields on top, the action list below. The framework writes the system prompt from these fields — a developer never types a prompt, and cannot accidentally A/B-invalidate one by rewording it.

Band C · Wire it to your game

the only C# the developer writes

Two files and one GameObject. This is where the framework hands control back — and the boundary the whole design depends on: the model never touches Unity. It emits three strings; the developer's handler is the only thing that moves a NavMeshAgent.

Step 05 — Say what each action does

A handler answers two questions: is this action legal right now, and what happens when it is chosen. The first one is the state-masking rule doing its work — an action whose IsAvailable returns false is not forbidden in the prompt, it is absent from the schema, so the model cannot express it.

A handler is never required to be its own file. Three actions as three methods on one VillageGuard.cs is the expected shape for a scene NPC — which is what the demo's script already is. Attributed methods, delegates, plain classes and MonoBehaviours are all adapted to the same IActionHandler. The separate-class version below is just the verbose end of the range, for a handler with enough state to deserve its own file.

Step 06 — The GameObject

Screen 2 from the sketch lab. A guard in the scene is an ordinary GameObject — Transform, NavMeshAgent, collider, mesh — with one extra component. That component is four references: which profile, which model, which handler runs which action, and the complete list of things this agent is allowed to name.

The other half of step 06 — what the agent notices

An agent needs two things from the world: the set of things it may name, and the facts it currently knows. Those come from the same component. An object a guard can notice and an object it can refer to are the same object, so Targetable carries both its id and its one line of description — which is what guarantees the sentence the agent reads and the id it may choose can never drift apart.

Step 07 — Decide when to ask

The framework never picks the moment and never classifies the reason (DR-008). There is no "dialogue mode" and no enum of situations. The developer calls DecideAsync from whatever already exists in their game: a submit button, an end-turn loop, a perception event, a timer. Three call sites, one API:

What happens in the second after that call

the whole framework in six steps

This is the picture to hold onto. Three lanes: the developer's code, our framework, and the model. The developer writes the first and the fifth step. Everything between them is what they installed the package for.

What the developer never does

  • ✕
    Never writes a prompt. It is generated from the profile. Rewording it by hand would invalidate every measurement we have.
  • ✕
    Never writes a JSON schema. It is built per request from what is available at that instant.
  • ✕
    Never parses the model's output. They receive a decision object, after the guards.
  • ✕
    Never edits framework source to add an action. That is the whole point of assets over an enum.
  • ✕
    Never lets the model reach Unity. It emits three strings; their handler is the only code that acts.
  • ✕
    Never hand-maintains "what can it do now". IsAvailable is asked at every decision.

Do we need a manager GameObject?

short answer: no, and that is a design rule

The question came up because most Unity AI packages want a singleton in the scene. Ours must not require one — a country in GreyBoxStrategy has no Transform, and an EditMode test has no scene at all. So there are two ownership patterns, and the shared plumbing belongs to neither.

What the developer ends up with on disk

one guard, three actions

Two trees, same guard, same three actions, same behaviour at run time. Which one you end up with is a choice about who edits the wording, not about what the framework can do.

Five decisions, argued and settled

DR-011 → DR-015 · 19–20 Sep 2026

These started as open questions on this page. Each was argued through and written into the build plan as a decision record. Two of them reversed the recommendation this page first carried — those reversals are kept visible below rather than quietly edited out, because the reasoning is the useful part.

1. How are actions and handlers authored? decided · DR-011

Both ways, over one plain data type. ActionDefinition is a plain serializable type in Core with no UnityEngine reference; ActionDefinitionAsset is a thin ScriptableObject wrapper holding one. Attributed methods and asset files are two front doors into the same registry, and a handler is never required to be its own file. On an id collision within one agent, the asset wins.

What it costs: every front door must be covered by the same Phase 1 EditMode assertions, as one parameterized fixture — three registration paths without that is three implementations that drift until a demo breaks. Attribute reflection also needs [Preserve] or a link.xml to survive IL2CPP stripping, which belongs in the Phase 6b player test rather than in a demo-day surprise.

2. Where does provider configuration live? decided · DR-013

A config asset, with a three-level resolution chain. Backend, endpoint, model, timeout, requests in flight and session budget live on a ScriptableObject, and several coexist — OllamaLocal, GeminiFlash. A Project Settings page names only the project default and the two evaluation arms. Resolution is agent override → scene override → project default, so an agent with an empty field just works.

What it costs: three places a value can come from. Paid off in the log window — the config that actually resolved is recorded per decision, so a misbehaving provider never needs guessing about which level won.

3. Where does the target list come from? decided · DR-014

Discovered from the scene, not typed per agent. The earlier answer — keep a hand-written list on every agent because it is the safety whitelist — did not survive the obvious objection: typing the same three landmarks on eight guards is authoring burden that starts to look like the behaviour tree this framework exists to replace. The whitelist has to exist at the instant of the decision; nothing requires it to have been typed.

So: a Targetable component marks an object nameable and carries its id, its one-line self-description and a category — deliberately the same component that supplies observations, so the line the agent reads and the id it may choose come from one place. An ITargetSource on the agent assembles the set per decision, by default a proximity and category query. A hand-supplied set stays available, and is what a country with no Transform uses. Two constraints: the same cap and nearest-first ordering as observations, because forty targetables within radius is a forty-value enum; and ids are explicit on the component, never derived from GameObject.name.

4. Can an agent decide on its own? decided · DR-015

Triggering stays yours; the call declares its priority. The first answer here was a flat no to any built-in trigger, on DR-008 grounds. Too strict — DR-008 forbids us classifying the situation, not shipping a trigger the developer configures. And it aimed at the wrong problem.

The real problem: every call currently looks identical to the queue, so when an ambient tick and a player's question arrive together the scheduler cannot know which one a human is waiting on. The fix is DecideOptions.Priority — player-facing by default, or background — set by whoever makes the call: a custom trigger, a coroutine, or a behaviour-tree node, which is a supported and expected integration rather than a workaround. An optional ticker component is sugar on top: off by default, no default interval, background priority, cancelled when the agent is disabled.

5. How does an agent learn what is around it? decided · DR-012

Pulled from observation sources at decision time, and capped. Per-call observations still work; this adds the path for agents that should notice rather than be told. Scene-reading sources live Unity-side so Core stays free of UnityEngine.

On the LLM summariser idea: supported, but as one source rather than a stage before every decision. Three conditions — cached and invalidated by an event, never per decision; registered target ids emitted verbatim, or the lexical grounding guard silently stops working; recorded as part of the arm in an eval run, because generated observations are non-deterministic input against a 10-point noise floor. Whether summarised beats templated is an early Phase 4 A/B, not an argument to settle now.

Phase 1 is pure C# with EditMode tests and no Ollama, on purpose: state masking, required target with the no_target sentinel, field order and the few-shot block are all testable without a model running. The first live decision is Phase 2. Every accuracy number quoted on this page is carried from the predecessor prototype (Appendix A) and was measured against Ollama specifically — it is not a claim about this framework until we re-measure it here, with a control arm, and write it into the findings log.
